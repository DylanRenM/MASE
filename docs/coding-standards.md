# MASE v2 跨语言编码规范

> 只在编码/评审任务加载；语言细节优先服从项目工具链和仓库规范。

## 1. 边界与类型

- 公共接口使用明确类型和业务命名，禁止无约束字典在模块间漂移。
- 在系统边界校验不可信输入；内部函数不重复无意义防御。
- API/公共协议保留 require/ensure/invariant 语义及契约测试。

## 2. 状态与所有权

- 业务状态只有一个事实来源；派生 View/报告不反向写状态。
- 资源、任务、文件描述符和回调必须有明确 owner、启动、取消和释放路径。
- 并发回调使用 session/token/identity 隔离迟到事件。

## 3. 错误处理

- 使用有类型、可恢复的业务错误；不吞异常，不把正常业务失败变成崩溃。
- Dev/CI 契约违反严格失败；Production 采用显式 relaxed 策略并记录证据。
- 失败路径保持原子性：不得发布半完成状态或遗留资源。

## 4. 安全与隐私

- 文件/归档限制类型、大小、深度、路径和解压总量。
- 不把密钥、文档内容、个人数据写入日志、遥测或备份。
- 命令、SQL、模板和反序列化不得拼接不可信输入。

## 5. 函数与模块

- 一个函数表达一个清晰行为；复杂度来源是业务分支时优先显式状态机而非隐藏技巧。
- 依赖方向指向稳定协议；系统框架通过 adapter 隔离以支持确定性测试。
- 复用必须降低总复杂度；不为假想需求提前抽象。

## 6. 测试可设计性

- 时间、随机、文件、网络和系统回调使用可替换 adapter。
- 测试观察行为和边界，不锁死实现细节。
- 禁止用 sleep 代替时序控制；性能测试记录环境和阈值。

## 7. 日志

- 结构化记录事件、稳定 ID、结果和耗时；不记录敏感正文。
- ERROR 表示需要处理的失败，WARN 表示降级或异常条件，INFO 表示低频业务里程碑。

## 8. 注释

- 注释解释“为什么”和约束，不翻译代码。
- TODO 必须带触发条件或追踪 ID；失效注释与代码一起修改。

## 9. 变更纪律

- 保持 diff 聚焦，保留用户无关改动。
- 删除、覆盖、迁移前备份；生成文件修改应回到规范源。
- 格式化、静态检查和编译器可验证的内容交给工具，不消耗模型评审 Token。

语言适配建议放入 `docs/coding/<stack>.md` 并按 stack 加载；现行核心规范不再内嵌 Python/TypeScript 示例或 OpenSpec 标记说明。

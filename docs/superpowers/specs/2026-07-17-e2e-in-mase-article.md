# E2E 测试在 AI 辅助软件工程中的定位、设计与实践

> 创建日期：2026-07-17
> 作者：Dylan Ren
> 摘要：本文总结 MASE（Measures AI Software Engineering）框架中关于 E2E 自动化测试的想法演进、设计决策与实践落地，从"为什么需要 E2E"到"E2E 如何嵌入六阶段流程"再到"环境隔离与指标闭环"，呈现一个完整的 E2E 工程化思考过程。

---

## 1. 引子：一个让人不安的事实

我们花了大量时间写单元测试，覆盖率做到 80% 以上，CI 流水线绿油油的——然而每次改完代码，还是要手工把页面点一遍，确认"功能没坏"。

这不是个别现象。在 AI 辅助开发场景下，代码产出速度大幅提升，但验证手段并没有同步升级。当 Agent 3 在一个 Session 里完成三个 Capability 的构建时，Agent 4 面对的是一张手工回归清单——逐个页面、逐个按钮、逐个场景去点。点一遍半小时，发现问题再修一遍，修完再点一遍。这不是验证，这是"人肉探伤"。

于是我们问自己一个问题：**如果手工回归测试是 E2E 自动化测试的穷亲戚，那我们为什么还要让开发者当这个穷亲戚？**

这成为 MASE 框架中 E2E 讨论的起点。

---

## 2. 三次迭代：从"能跑就行"到"门禁级工程化"

我们对 E2E 的认识经历了三个阶段的迭代，每个阶段都在解决前一阶段暴露出的更深层问题。

### 2.1 第一轮（2026-07-12）：让 E2E 先跑起来

最初的想法很朴素：给 Pilot 项目（COSMIC/NESMA 智能度量平台）写几个 Playwright 测试，覆盖登录、度量、知识库等 6 个核心场景，能一键回归就行。

这一轮确定了几项基础决策，后来被证明是正确的：

- **语义定位优先**：`getByRole()` > `getByLabel()` > `getByPlaceholder()` > `getByText()` > `getByTestId()`。禁止 CSS class/id 选择器。原因很简单：CSS class 是给样式写的，UI 重构时必然失效；语义定位器描述的是"用户看到了什么"，天然抗 UI 变化。
- **数据与测试分离**：`seed.py` 生成 `fixtures.json`，测试只读不写。这借鉴了 skills-hub 的 Fixture Runner 模式，并行安全且可重复。
- **双轨制**：Playwright 原生 runner 做回归（完整 trace/screenshot/video），Python `debug.py` 做调试（灵活内省）。回归和调试分轨，互不干扰。
- **测试数据库隔离**：`pilot_test.db` 独立于开发库，配合 `--test` 参数启动应用。

第一轮的目标很小：6 个场景，能跑通就行。事实上跑通了，而且意外发现了一批按钮交互测试的盲区——那些"切 Tab、点 Radio、清空输入框"等没人记得测的操作，被 E2E 自动化捡了回来。

### 2.2 第二轮（2026-07-14）：E2E 不能只是一层皮

第一轮做完后，一个问题浮现出来：**E2E 测试是项目级的临时决定，还是框架级的工程约束？**

如果是前者，每个项目自己决定写不写、写多少，E2E 就永远是"锦上添花的好东西"而不是"必做项"。如果是后者，E2E 必须嵌入 MASE 的核心流程——从需求定义阶段就开始想 E2E，而不是代码写完了才补。

这就是第二轮讨论的核心：**E2E 在 MASE 框架中的定位与强化**。

我们比较了三种方案：

| 方案 | 描述 | 优点 | 缺点 |
|:---|:---|:---|:---|
| A：全链路嵌入 | E2E 要求嵌入 Proposal → Design → Build → Verify 四个阶段 | 完整闭环，从源头驱动 | 改动面大 |
| B：Verify 门禁 | 仅在 Verify 阶段加 E2E 回归门禁 | 改动最小 | 变成"事后补票"，可能成瓶颈 |
| C：分三期落地 | 先做 Verify，再做 Build，最后做 Proposal | 风险最低 | 完整价值实现周期长 |

最终选择了方案 A。理由很简单：**如果 E2E 只在 Verify 阶段出现，开发者在 Build 阶段不会为 E2E 预留接口和结构，最后必然是硬编码选择器、绕过 Page Object、测试和数据耦合——这正是我们第一轮就已经否定的做法。**

方案 A 带来的核心变化：

1. **Proposal 阶段新增 E2E 验收场景**：Agent 2 在需求澄清时同步定义 P0/P1/P2 场景，其中 P0 = 核心业务流程，**必须 100% E2E 覆盖**。没有这条约束，"核心流程"就是各说各话的概念。

2. **Build 阶段 TDD 外循环**：在原有的 RED → GREEN → REFACTOR 内循环之外，增加一个外层循环——功能实现后同步编写 E2E 测试。内循环保证代码正确，外循环保证用户体验正确。

3. **Verify 阶段双轨制门禁**：自动化 E2E 回归（P0 100% 硬门禁）+ 人工探索性测试（创造性探索，不重复 E2E 已覆盖的）。人工从"苦力"解放为"猎手"。

4. **Retro 阶段指标闭环**：P0 覆盖率、BUG 拦截率、回归执行时间作为复盘指标，未达标触发根因分析。

### 2.3 第三轮（2026-07-17）：测试把环境搞脏了怎么办

第二轮设计完成后，我们在 Pilot 项目上实际执行 E2E 回归时发现了新问题。

E2E 场景不只是"只读操作"——真实的验收场景必然涉及写操作：修改系统设置、上传文件、变更配置项。而当前的环境隔离仅在数据库层面做了 `pilot_test.db` + `seed.py` 重建，**文件系统、配置文件、环境变量完全没有保护**。

这意味着：一次 E2E 回归跑完，上传目录可能残留了测试文件，`.env` 可能被改了 debug 开关，导出目录多了一堆测试 Excel。下次回归时，这些"脏状态"可能让测试行为不确定。

这是根因分析的标准场景：问题不在测试代码，而在于**设计假设（"E2E 只读"）与实践（"验收必然写"）之间的断层**。

解决思路是 **E2E Sandbox 三层防线**：

```
第一层：状态快照与恢复 (Snapshot & Restore)
  beforeAll: 快照文件树哈希 + 配置项值 + 环境变量
  afterAll:  增删改三向对齐恢复 + 恢复后验证一致性

第二层：写入重定向 (Write Redirection)
  数据库：已有 pilot_test.db 隔离（不变）
  文件：通过环境变量重定向上传/导出/日志到 e2e/sandbox/ 临时目录

第三层：环境健康检查 (Environment Health Check)
  关键文件完整性、端口占用、数据库可读性
  异常时 Block 后续测试 + 输出清理指南
```

关键设计决策：

- **快照恢复用"增删改"三向对齐**：新增文件删除、修改文件回滚、删除文件报错（不能自动恢复，需人工确认）。
- **配置文件用值级恢复而非文件级恢复**：避免整体覆盖文件时丢失并发进程的正常写入。
- **Sandbox 对测试代码零侵入**：通过 `beforeAll`/`afterAll` 中的 `sandbox.snapshot()` / `sandbox.restore()` / `sandbox.verify()` 三连调用实现，测试用例不需要写任何清理逻辑。

第三轮完成后，E2E 测试基础设施从"能用"进化为"可信"——每次回归后环境的干净程度可以被程序验证，而非靠开发者自觉。

## 3. E2E 在 MASE 六阶段中的完整嵌入

经过三轮迭代，E2E 在 MASE 框架中已不是某个阶段的附加品，而是贯穿 Proposal → Design → Build → Verify → Retro 五个阶段的一等公民。

### 3.1 Proposal 阶段：定义 E2E 验收场景

Agent 2 在需求澄清时，除了写系统测试用例，还要定义 E2E 验收场景。每个场景包含：

- 场景名称、用户故事、前置条件
- 操作步骤（用户在浏览器中的完整操作路径）
- 预期结果（可程序验证的断言）
- 优先级：**P0（核心流程，必须测）/ P1（重要辅助）/ P2（边缘场景）**

这意味着一件事：**"这个功能怎么验收"不是在代码写完之后才想的，而是在需求定义阶段就定下来的。**

Agent 2 同时在 `.openspec.yaml` 中声明 `has_ui: true/false`——这是后续所有 E2E 门禁的触发条件。CLI、API、库项目天然豁免，不会有额外负担。

### 3.2 Design 阶段：规划 E2E 测试策略

Agent 3 在 `architecture.md` 中新增 "E2E 测试策略"章节，回答四个问题：

1. **Page Object 怎么组织？** 哪些页面独立封装，哪些组件共享？
2. **fixtures 数据怎么准备？** 测试数据库隔离策略 + seed.py 设计
3. **元素怎么定位？** 遵循语义定位器优先级规范
4. **测试环境怎么配？** baseURL、webServer 启动方式、环境变量注入

这些策略不应该是"测试代码怎么写"的微观指导——那是 Playwright 规范的事。它应该回答：**这个项目的 E2E 测试体系的顶层框架长什么样。**

### 3.3 Build 阶段：TDD 外循环

这是最容易被跳过的环节。Agent 3 在写完功能代码后，天然倾向于"功能好了，下一题"，补 E2E 测试的动机很弱。

所以我们把 E2E 测试编写**嵌入 Build 阶段的 10 步微循环**，作为第 6 步强制执行：

```
1. 复用检查
2. 契约翻译 → 测试（RED）
3. 写单元测试（RED）
4. 写实现代码（GREEN）
5. 跑单元/集成/契约测试
6. E2E 测试  ← 这里！同步编写 Playwright 测试
7. 功能测试（webapp-testing 调试）
8. 代码评审
9. 安全扫描
10. git commit
```

逻辑很直接：**单元测试验证代码逻辑正确，E2E 测试验证用户看到的东西正确。两者不是替代关系，是互补关系。** 一个功能只有通过了第 5 步和第 6 步，才算"Build 完成"，才能进入 Verify。

### 3.4 Verify 阶段：自动化回归 + 人工探索双轨制

这是 E2E 价值最大化体现的阶段。Verify 阶段的门禁流程：

```
① 执行全量 E2E 回归（Playwright --grep @P0）
   ├── P0 全部通过 → 门禁通过，进入人工探索
   ├── P0 有失败 → bug-fixer 微循环修复
   └── 同一场景连续 3 次修复仍失败 → 升级 Agent 1 决策
       （是设计缺陷？回退 Design。是需求变更？回退 Proposal。）

② 人工探索性测试
   只做创造性探索——试奇怪输入、测边界条件、找 E2E 覆盖不到的视觉/体验问题
   不再重复点击 E2E 已经验证过的流程

③ 测试缺口复盘
   E2E 没拦截的 BUG → 为什么没拦住？→ 补充 E2E 用例

④ 门禁：全部 BUG 关闭 + P0 100% 通过
```

这里有两个关键设计：

**连续 3 次失败的升级机制**：不是让 Agent 4 反复修同一个问题，而是强迫停一下，问"是不是根因不在代码层面？"——可能是设计阶段的架构决策导致的，可能是 Proposal 阶段的需求定义就不对。这是根因分析原则在门禁流程中的具体体现。

**测试缺口反哺**：每一个被人工探索发现的 BUG，都要问一句"为什么 E2E 没拦住？"，然后补充 E2E 用例。这就是指标闭环——不是跑完 E2E 就完了，而是通过 E2E 的"漏网之鱼"反向改进 E2E 本身。

### 3.5 Retro 阶段：指标驱动改进

复盘报告新增 E2E 测试指标章节，三个核心指标：

| 指标 | 定义 | 阈值 |
|:---|:---|:---|
| P0 E2E 覆盖率 | E2E 覆盖的 P0 场景数 / P0 场景总数 | = 100%（硬门禁） |
| BUG 拦截率 | E2E 发现的 BUG 数 / Verify 阶段总 BUG 数 | ≥ 80%（软目标） |
| 回归执行时间 | 全量 E2E 回归耗时 | ≤ 10 分钟（观察指标） |

BUG 拦截率未达标时，Retro 必须产出根因分析：
- 是 Proposal 阶段 P0 场景定义缺失？→ 改进场景定义流程
- 是 Build 阶段 E2E 测试没写？→ 门禁为何没拦住？改进门禁执行
- 是某些 BUG 类型天然无法 E2E 覆盖（如视觉渲染）？→ 标记为人工探索专属

跨轮次的指标趋势写入 `project_memory.md`，供 Agent 1 在下轮 Proposal 时评估项目的 E2E 健康度。

## 4. 工程实践：几个值得说的设计选择

### 4.1 为什么不追求 100% 覆盖率？

E2E 资源消耗远高于单元测试——一个 E2E 用例从启动浏览器到完成断言，耗时是单元测试的几十倍。追求 100% 场景覆盖意味着回归时间膨胀到不可接受。

我们的策略是 **P0 场景 100% 覆盖，P1 应当覆盖，P2 人工探索**。这不是偷懒，是 ROI 最大化——用有限的回归时间覆盖"出问题后果最严重"的场景。

### 4.2 元素定位为什么禁止 CSS class？

软件工程里有一个反复被验证的教训：**和 UI 实现细节耦合的测试，一定会在 UI 重构时大面积失效。**

CSS class 是给样式写的——这一版用 `btn-primary`，下一版可能重构为 `button--primary--large`。如果你用 `page.locator('.btn-primary')` 定位，UI 重构时所有测试全红，但功能其实没问题。这是**假阳性**——测试失败的原因不是功能坏了，而是测试写得太脆弱。

语义定位器（`getByRole('button', { name: '登录' })`）绑定的是"用户眼中的按钮"，而不是"开发者写的 CSS class"。只要按钮还在且叫"登录"，测试就不会因为 UI 重构而失效。

### 4.3 为什么不直接用 Docker 做环境隔离？

Docker 是完美的隔离方案——但我们刻意没有选它。原因是 MASE 定位为**轻量级 AI 辅助开发框架**，不应强制要求 Docker 作为基础设施依赖。一个开发者 clone 代码后应该能直接跑 `npx playwright test`，而不是先 `docker-compose up`。

快照恢复 + 写入重定向的方式在隔离强度上不如 Docker，但在**零基础设施依赖**和**开发者体验**上完胜。这是有意的 trade-off，不是能力不足。

### 4.4 BUG 拦截率为什么是软目标？

P0 覆盖率是硬门禁（不通过不能进下一阶段），但 BUG 拦截率是软目标（Retro 分析但不阻断 Release）。

原因是：BUG 拦截率的分子（E2E 发现的 BUG）和分母（总 BUG）高度依赖于 BUG 的定义粒度——有的项目拆分细（每个问题一个 BUG），有的项目拆分粗（一个 BUG 包含多个子问题）。这使得拦截率在不同项目之间不可比。

所以我们把它定位为**趋势指标而非门禁指标**——同一个项目上一轮 85%、这一轮 72%，说明有问题要分析；但不能说"你拦截率不到 80%，不能发布"。

## 5. 阶段性成果与经验

### 5.1 实践验证

在 Pilot 项目中，E2E 体系经历了从零到完整的过程：

- 首期 6 个 spec 文件，从 60 条测试增长到 109 条
- P0 场景（登录/度量全流程/知识库管理）13 条测试全部通过
- 从干净状态一键运行，9 秒完成 P0 回归
- 发现了一批手工测试容易遗漏的交互场景（Tab 切换、Radio 切换、清空按钮等）

### 5.2 核心经验

1. **E2E 不是"写完代码再补"的事后活**。如果不在 Proposal 阶段定义验收场景，Build 阶段就不会写 E2E，Verify 阶段就只能手工点。全链路嵌入是让 E2E 从"可选"变成"必选"的唯一方式。

2. **环境隔离不是可选的 nice-to-have**。E2E 测试必然涉及写操作，"只读假设"是一个在实践中被反复打破的美好愿望。快照恢复机制将"环境干净"从开发者自觉变成了可编程验证的工程约束。

3. **指标闭环比指标本身更重要**。P0 覆盖率和 BUG 拦截率的意义不在于数字好看，而在于它们驱动了 Retro 阶段的根因分析——"为什么 E2E 没拦住这个 BUG？"这个问题问出来，E2E 体系就开始自我进化了。

4. **轻量优于完备**。不引入 Docker、不强制复杂基础设施、不修改四 Agent 分工和六阶段顺序。E2E 是框架的增强，不是框架的重构。

## 6. 展望

E2E 在 MASE 框架中仍有两个方向值得继续探索：

1. **跨项目 E2E 模式提炼**：目前的实践集中在 Pilot 这一个 Web 项目。当更多有 UI 的项目接入 MASE 后，E2E 的通用模式（Page Object 组织、fixtures 设计、Sandbox 配置）能否提炼为标准模板，减少每个项目的重复设计？

2. **AI 辅助 E2E 用例生成**：Agent 2 在 Proposal 阶段定义了验收场景后，Agent 3 能否基于场景描述 + Page Object 自动生成 E2E 测试骨架？这不是替代手写测试，而是减少"翻译场景到代码"的机械劳动。

E2E 自动化不是银弹——它解决不了视觉渲染、交互体验、非确定性输出等需要人工判断的问题。但它能做一件关键的事：**把人类从"确认功能正常"的重复劳动中解放出来，让人去做机器做不了的事。** 这就是 MASE 框架中 E2E 的根本价值。

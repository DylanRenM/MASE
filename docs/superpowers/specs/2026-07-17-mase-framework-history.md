# MASE 框架的前世今生：一套 AI 软件工程方法论的诞生与演化

> 创建日期：2026-07-17
> 作者：Dylan Ren
> 阅读时长：约 25 分钟

---

## 前言

2026 年 7 月，MASE 框架发布 v1.3。四 Agent、六阶段、九大工程原则、十二个 Skills、三层质量防线——这些数字背后，是一段从混乱到秩序、从碎片到体系的演化历程。

本文试图完整记录 MASE 的来龙去脉：它从什么样的工程困境中诞生？每一轮迭代解决了什么问题？背后的设计哲学是什么？如果你正在构建自己的 AI 辅助开发流程，或者想理解为什么"AI 编程更需要工程化"，这篇文章或许能提供一些参考。

---

## 第一章：黎明之前 — AI 编程的"狂野西部"

### 1.1 工具有了，纪律没有

2026 年上半年，AI 编程工具已经相当成熟。Trae、Cursor 等 IDE 让开发者可以"用嘴写代码"——描述需求，AI 生成实现。效率是惊人的，但问题也同样惊人：

- **风格飘忽**：同一个功能，前一次生成用 Factory 模式，后一次变成了直接 new 对象。LLM 每次采样不同，代码风格来回跳。
- **步骤跳跃**：AI 天然倾向于"直接给答案"。你问"怎么实现登录"，它跳过需求分析、跳过架构设计、跳过测试，直接给你一段 `app.post('/login', ...)` 的实现代码。
- **质量黑洞**：没有评审门禁的情况下，AI 生成的代码就是"写了就上线"。BUG 累积到不可收拾的程度，才开始惊慌失措地修。
- **知识流失**：这次踩的坑——"那个库的 v2 版本 API 不兼容"——下次还会踩。因为经验存在人脑子里，没有进入流程。

这不是某个工具的问题，而是**人机协作模式**的固有问题。人类开发者有工程纪律意识但常常偷懒，AI 有执行力但没有纪律意识。当两者协作时，最容易被牺牲的就是工程纪律。

### 1.2 三层能力，各自精彩也各自孤单

在 MASE 诞生之前，我们其实已经有了两层不错的能力：

**第一层：OpenSpec — 规范驱动开发**

OpenSpec 解决的是"规范怎么写"的问题。它以 changeset 为单位，用 proposal → design → specs → tasks 的结构化流程，让每个功能变更都有清晰的 Why / What / How。通过 Gherkin 风格的 spec.md 定义可验证的验收标准，让 AI 不再"凭感觉写代码"，而是"对着规格写代码"。

**第二层：Superpower / Skills — 单点能力强化**

Skills 解决的是"具体任务怎么做"的问题。brainstorming 做需求澄清，bug-fixer 做智能修复，code-review 做合规检查，test-driven-development 做 TDD 微循环……每个 Skill 都是某个垂直领域的高度专业化 Agent。

但两层之间有一道鸿沟。

OpenSpec 的强项是**规范产出结构化**，但规范写好了之后呢？谁来执行？谁在执行前审查？执行后谁验证？验证发现的问题谁来追踪闭环？这些问题 OpenSpec 不管。

Superpower 的强项是**单点任务专业化**，但单点再强，拼不起来还是一盘散沙。brainstorming 澄清了需求，需求如何流转到设计？code-review 发现了问题，问题如何确保被修复？bug-fixer 修了一个 BUG，类似 BUG 如何被系统性预防？这些问题 Skills 不覆盖。

**两层都很好，但它们之间没有"胶水"。**

### 1.3 实践中的碎片化

在 MASE 之前的实际项目中，这种碎片化随处可见。以 Bazi 命理百科全书项目为例，它涉及：

- 363 本电子书的格式转换与内容清洗
- 基于 LLM 的文本规范化与广告去除
- 向量化、语义分块、去重、百科编排
- 前后端分离的 Web 应用

项目本身有着清晰的设计文档（预处理层升级设计、管道质量升级设计），但在执行层面，研发活动是"对话驱动"的——今天修一个 BUG，明天加一个功能，后天重构一个模块。没有阶段概念、没有门禁机制、没有复盘闭环。每次对话都在"原地打转"，因为没有流程告诉 Agent"现在应该做什么"。

这种状态在当时是我们所有 AI 辅助项目的常态。工具是好的，人是努力的，但**过程是混乱的**。

## 第二章：诞生 — 把碎片拼成体系（2026-07-03）

### 2.1 核心洞察：AI 编程的三个缺失

经过多轮讨论，我们提炼出 AI 辅助编程的三个系统性缺失：

1. **流程缺失**：没有从需求到发布的完整路径。Agent 不知道该先做什么后做什么，每次都从零开始判断。
2. **门禁缺失**：没有"做完"的客观标准。什么算需求澄清完成？什么算设计评审通过？什么算可以发布？没有答案。
3. **进化缺失**：经验无法沉淀。一个项目踩的坑，下一个项目继续踩。这一轮犯的错，下一轮还会犯。

这三个缺失不是某个工具的问题，而是**层与层之间**的问题。OpenSpec 管了规范层，Skills 管了能力层，但两者之间的"编排层"是空白。

### 2.2 "一拖三"架构的诞生

2026 年 7 月 3 日，第一版 MASE 统一开发框架设计文档诞生。核心架构可以用九个字概括：**四 Agent · 六阶段 · PDCA 闭环**。

```
                      用户
                       │
                       ▼
┌──────────────────────────────────────────────┐
│        Agent 1: 计划与统管 (Orchestrator)       │
│    接收需求 → 分解 → 调度 → 门禁 → Release       │
└──────┬────────────┬────────────┬──────────────┘
       │            │            │
       ▼            ▼            ▼
┌──────────┐ ┌────────────┐ ┌──────────────┐
│ Agent 2  │ │  Agent 3   │ │   Agent 4    │
│  需求     │ │   开发      │ │    质量       │
└──────────┘ └────────────┘ └──────────────┘
```

四个 Agent 的分工逻辑非常朴素：

- **Agent 2（需求）**只做需求澄清和原型确认。它不写代码，不参与设计评审，不对代码质量负责。这确保了需求阶段不会被"怎么写"的思维污染。
- **Agent 3（开发）**承担最重的职责——技术预研、架构设计、详细设计、TDD 构建。设计和编码是同一个人格做出的决策，更连贯。但它不评审自己的代码。
- **Agent 4（质量）**是独立的质量守护者。它评审 Agent 3 的设计和代码，执行端到端验证，修复 BUG，做复盘分析。**写代码的人不评审自己的代码**——这是多 Agent 架构的第一性原理。
- **Agent 1（统管）**不执行具体任务，只做调度和门禁。它是"项目经理 + 监理工程师"的合体，确保流程不走样。

### 2.3 六阶段：PDCA 的完整闭环

MASE 的六阶段直接映射到 PDCA 循环：

```
Proposal → Design → Build → Verify → Retro → Release
  (Plan)    (Plan)    (Do)    (Check)   (Act)   (Deliver)
```

| 阶段 | 谁执行 | 核心动作 | 为什么存在 |
|:---|:---|:---|:---|
| Proposal | Agent 2 | 需求澄清 + 原型确认 + 验收场景定义 | 不确认方向不开工。AI 猜错需求不是写错一行，是批量生成一个方向的错误代码 |
| Design L1 | Agent 3 | 技术预研 + POC 验证 | 所有外部依赖在本环境先跑通。不做"应该可以"的假设 |
| Design L2 | Agent 3 | 架构设计 + Gherkin Spec + 契约推导 | 先想清楚怎么做，再动手做。Architecture → Spec → Contract，逐层细化 |
| Build | Agent 3+4 | TDD 10 步微循环 | 每个 Scenario 独立开发、独立测试、独立提交。小步快跑 |
| Verify | Agent 4 | E2E 回归 + 人工探索 + Bug 修复 | 自动化回归省时间，人工探索找盲区，修一个防一类 |
| Retro | Agent 4+1 | 复盘分析 + 流程改进 | 经验不悬空，变成下一轮的规则 |
| Release | Agent 1 | 合规审查 + git commit + 文档归档 | 最后一次全量检查，确保发布质量 |

值得特别说明的是 **Design 拆成 L1 和 L2 两层**的设计。这不是过度拆分，而是经验教训——在早期实践中，架构设计经常因为某个外部依赖不可用而推倒重来。把技术预研独立为一个子阶段（L1），在所有外部依赖跑通之后再做架构设计（L2），避免了"设计好了才发现依赖不 work"的返工。

### 2.4 最初的原则体系

第一版 MASE 定义了 6 条核心原则，后来陆续扩展到 9 条。原则的设计遵循一条元规则——**三次法则**：同一问题、同一模式、同一类错误在第三次出现时，就是系统化改进的最佳时机。

初版六原则：

1. **设计先行，方向确认再实现** — 不写一行代码前，先确认方向
2. **TDD 内外双循环** — Spec 驱动验收 + 测试驱动编码
3. **系统性解决问题，不做临时补丁** — 修一个 BUG 防一类 BUG
4. **需求澄清优先，原型确认优先** — 1:10 定律：前期花 1 分钟澄清 = 后期省 10 倍返工
5. **根因分析，不盲目修改** — 找到根本原因，不只修表象
6. **经验沉淀，每次都要学一次** — 踩过的坑不进文档等于白踩

### 2.5 三层架构的明确定位

MASE 不是要替代 OpenSpec 和 Skills——它在它们之上构建了编排层：

```
┌──────────────────────────────────────────┐
│              MASE（编排层）                  │
│   四 Agent 协作 · 六阶段流转 · PDCA 进化     │
├──────────────────────────────────────────┤
│  OpenSpec 层（规范层）                       │
│   proposal / design / specs / tasks       │
├──────────────────────────────────────────┤
│  Superpower / Skills 层（能力层）            │
│   brainstorming / TDD / code-review / ... │
└──────────────────────────────────────────┘
```

三者各司其职：
- **OpenSpec** 管"规范怎么写" → 产出结构化的 proposal、specs、tasks
- **Skills** 管"具体任务怎么做" → 提供专业化执行能力
- **MASE** 管"整个过程怎么跑" → 调度 Agent、流转阶段、执行门禁、驱动改进

这个三层架构回答了 MASE 的核心价值：**把碎片化的好工具编排成一套自洽、可进化的软件工程方法论。**

## 第三章：夯实 — 从概念到体系（2026-07-03 ~ 07-08）

### 3.1 框架文档体系化

框架设计文档完成后，紧接着建立了一整套支撑性规范文档：

- **项目结构规范** (`project-structure-spec.md`)：五层目录架构（src + tests + docs + openspec + config），三大原则（唯一性、镜像、Capability 对齐）
- **编码规范** (`coding-standards.md`)：9 章跨语言通用规范，涵盖命名、硬编码、函数设计、错误处理、日志、导入、注释、DRY
- **设计原则** (`design-principles.md`)：SOLID 5 + GRASP 9 + 通用原则 9 + 分层原则 5，共 30 条，每条标注 MASE 评审重点
- **术语表** (`glossary.md`)：核心术语精确定义，解决"契约""外循环"等词汇的多义混乱问题
- **使用手册** (`user-guide.md`)：从项目初始化到发布的全流程操作指南

这些文档不是装饰。它们是**按需加载的知识库**——Agent 在特定场景下读取对应的规范文件，而不是把所有规则都塞进常驻内存。这背后是一个重要的 token 优化策略：原则文件（常驻）越短越好，规范文件（按需）越详细越好。

### 3.2 培训体系建立

7 月 7 日至 8 日，MASE 框架的第一版培训 PPT 完成。37 页，16:9 宽屏，深蓝背景 + 金色标题 + 青色强调色。

这个 PPT 的迭代过程本身就是一次 MASE 方法论的小规模实践。初版用 HTML 生成后转 PPTX，排版混乱。第二轮改用 Playwright 截图方案，布局完美但文字不可编辑。第三轮深度重构文本引擎，用递归树遍历、Flex/Grid 容器处理、文本高度预估等策略重新生成，最终产出了布局正确且文字可编辑的版本。

这个过程暴露出一个反复出现的问题：**设计细节的持续打磨需要多轮迭代**——而这恰好是 MASE 框架中 Build → Verify 循环的微观体现。每一次排版问题的修复，都对应着一个"发现 → 分析根因 → 修改 → 验证"的微循环。

### 3.3 八层架构的方法论提炼

在培训材料整理过程中，MASE 的架构被进一步抽象为**八层参考架构**，作为"如何搭建自己的 AI Coding 过程框架"的方法论输出：

```
1. 原则层 (Principles)   — 常驻内存，全程遵守
2. 规则层 (Rules)        — 按需加载，场景触发
3. 职责层 (Agents)       — 角色分工，各司其职
4. 阶段层 (Phases)       — 流程串联，门禁把关
5. 技能层 (Skills)       — 动作拆解，流程标准化
6. 质控层 (Quality)      — DoD + Checklist + 三级门禁
7. 输出层 (Outputs)      — 模板 + 目录结构 + 文档规范
8. 工具层 (Tools)        — CLI + 依赖 + 环境
```

这八层不是 MASE 特有的——它是**任何 AI 辅助开发过程框架的通用设计模式**。每一层回答一个不同的"怎么做"问题，从抽象（原则）到具体（工具）逐层递进。如果读者正在设计自己的开发流程，这八层架构可以作为参考模板。

## 第四章：强化 — 三道防线成型（2026-07-14）

2026 年 7 月 14 日是 MASE 框架演化中最密集的一天。三项重大强化在同一天完成设计：契约式开发（DbC）、E2E Playwright 全链路嵌入、以及项目历史迁移。

### 4.1 项目整合：把散落的历史拼回来

在 7 月 14 日之前，MASE 相关的讨论分散在多个项目中——日常办公项目有 PPT 产出，SOLO Agent 项目有 E2E 讨论，不同日期的 session 记忆互不连通。

这一天做了三件事：

1. **GitHub 仓库下载**：通过 curl + Python zipfile 方案获取 MOSE GitHub 仓库内容
2. **无关内容清理**：删除成本度量、八字命理等非 MASE 内容，所有删除文件备份到 `.backup/`
3. **知识迁移**：将 Spec/契约/TDD 融合文档、Playwright 测试规范、API 契约测试等内容迁移到 MASE 项目

迁移完成后，MASE 项目成为所有相关讨论的"单一事实来源"——后续所有讨论自动累积到同一个 memory 目录，不再分散。

### 4.2 契约式开发（DbC）的纳入

这是 MASE 框架最根本的一次强化。在加入契约层之前，MASE 有三道防线：

- **Spec**：Gherkin 验收规格，管"要做什么"
- **TDD**：单元测试 + 集成测试，管"行为正确"
- **E2E**：（当时还在设计中）端到端回归，管"用户视角正确"

但缺少了最关键的一层：**正确性的边界在哪？**

Spec 告诉你"用户登录成功后应该跳转到首页"，TDD 用测试验证这个行为。但 Spec 不告诉你"用户名为空时应该返回什么错误码"，TDD 的测试可能因为开发者没想到这个边界条件而漏掉。

契约（DbC）补上了这个缺口：

- **前置条件（require）**：调用前必须满足什么
- **后置条件（ensure）**：调用后必须保证什么
- **不变式（invariant_check）**：操作前后什么不变

契约从 Gherkin Spec 中推导——每个 Scenario 的 Given/When/Then 隐含着前置条件和后置条件。推导出的契约以 `contract.md` 形式独立存在，然后在 Build 阶段被翻译为两样东西：TDD 测试用例和运行时断言。

契约的纳入将 MASE 的原则从 8 条扩展到 9 条，新增第 3 条"契约式约束"：

> 从 Spec 推导 DbC 契约（前置/后置/不变式）。API 级硬性必做，模块级强推荐，函数级可选。TDD 翻译契约到测试，代码保留运行时断言。

这个修改的意义在于：契约从"可选最佳实践"变成了"框架级工程原则"。不是"建议你写契约"，而是"不写契约过不了 Design L2 门禁"。

### 4.3 E2E 全链路嵌入

与契约同步进行的，是 E2E 测试在 MASE 框架中的全面强化。这部分在[E2E 测试在 MASE 中的定位、设计与实践](2026-07-17-e2e-in-mase-article.md)一文中有详尽阐述，这里只概述关键变化：

- **Proposal 阶段**：Agent 2 在需求澄清时定义 P0/P1/P2 E2E 验收场景
- **Design 阶段**：Agent 3 在 architecture.md 中规划 E2E 测试策略（Page Object 组织、fixtures 设计、定位策略）
- **Build 阶段**：E2E 测试编写嵌入 TDD 10 步微循环的第 6 步，强制执行
- **Verify 阶段**：自动化 E2E 回归（P0 100% 硬门禁）+ 人工探索性测试双轨制
- **Retro 阶段**：P0 覆盖率、BUG 拦截率、回归执行时间三项指标驱动改进

原则第 4 条从笼统的"端到端验证"升级为明确的"E2E 自动化回归 + 人工探索性测试 + 合规审查"。

### 4.4 此时的三道防线全景

契约和 E2E 强化完成后，MASE 的质量防线体系成型：

```
防御层          手段                    门禁级别
─────────────────────────────────────────────
Spec           Gherkin 验收规格          Build 门禁
Contract       DbC 前置/后置/不变式      Design L2 + Build 双重检查
TDD            单元测试 + 集成测试        Build 微循环（每个 Scenario）
E2E            Playwright 全量回归       Verify 硬门禁（P0 100%）
运行时断言      require/ensure/invariant  Build 门禁（代码级）
合规审查        code-review + security    Build 旁路 + Release 门禁
```

六道防线，从需求定义（Spec）到用户视角（E2E）全覆盖。每一道防线都有自己的检查手段和门禁级别，形成了纵深防御。

## 第五章：精化 — 让基础设施可信（2026-07-17）

### 5.1 E2E 环境隔离：从"能用"到"可信"

契约和 E2E 强化设计完成后，在 Pilot 项目上实际执行 E2E 回归时，暴露了一个深层问题：E2E 测试会"弄脏"环境。

真实的验收场景必然涉及写操作——修改系统设置、上传文件、变更配置。但当前的隔离机制只在数据库层面做了保护，文件系统、配置文件、环境变量完全暴露。一次回归跑完，上传目录残留测试文件，`.env` 可能被改了 debug 开关，下次回归的行为就不确定了。

这是根因分析的标准场景：问题不在测试代码，而在于**设计假设（"E2E 只读"）与实践（"验收必然写"）之间的断层**。

解决方案是 E2E Sandbox 三层防线：

- **第一层：状态快照与恢复** — beforeAll 快照文件哈希 + 配置值 + 环境变量 → afterAll 增删改三向对齐恢复 + 一致性验证
- **第二层：写入重定向** — 通过环境变量将上传/导出/日志重定向到 `e2e/sandbox/` 临时目录
- **第三层：环境健康检查** — 恢复后自动验证关键文件完整性、端口占用、数据库可读性

关键设计决策：**不用 Docker**。MASE 定位为轻量级 AI 辅助开发框架，不应强制要求 Docker 作为基础设施依赖。快照恢复 + 写入重定向在隔离强度上不如 Docker，但在零基础设施依赖和开发者体验上完胜。这是有意的 trade-off。

### 5.2 框架 v1.3：稳定化与自审

同日，MASE 框架文档更新至 v1.3。主要变化：

- 原则从 8 条正式确认为 9 条（R01-R09）
- E2E Sandbox 机制纳入 Verify 阶段流程
- Build 阶段 10 步微循环中明确 E2E 测试位置（第 6 步）
- Skills 映射表更新（12 个 Skills × 6 阶段矩阵）
- 术语表新增 E2E Sandbox 相关 5 个术语定义

v1.3 的发布标志着 MASE 从"快速演化"阶段进入"稳定迭代"阶段。框架的核心架构——四 Agent、六阶段、九原则——已经稳定，后续的变化更多是在已有框架内的增强和精化。

## 第六章：设计哲学 — MASE 背后的思考

### 6.1 "AI 编程更应工程化"的悖论

MASE 最核心的信念是一个看起来矛盾的陈述：**AI 编程更应该工程化，因为 AI 放大了混乱的代价；AI 编程更能工程化，因为 AI 具备人类没有的执行力。**

传统软件工程中，流程和规范常常被抵触——不是它们不对，而是执行起来太累。人类开发者天性喜欢即时反馈（写代码、看效果），厌恶延迟满足（写文档、做评审、跑测试）。

AI 没有这些"人性弱点"。它不觉得枯燥，不需要自律，不厌倦重复。它擅长处理繁琐、保持一致性、严格守规矩。这意味着：

- 人类怕约束所以爱敏捷 → AI 守规则所以爱工程化
- 人类跳过测试因为"应该没问题" → AI 不会跳过，除非你让它跳过
- 人类文档滞后因为"回头再补" → AI 可以在编码的同时更新文档

**人负责定义与决策，AI 负责执行与守规**——这是 MASE 的人机协作哲学。

但同时，AI 也放大了混乱的代价。人类开发者猜错需求，可能写错几十行代码。AI 猜错需求，批量生成一个方向的错误代码。模糊性是返工成本的最大来源，而 AI 让模糊性的代价指数级上升。所以**越是用 AI 编程，越需要前期的需求澄清和后期的质量门禁**。

### 6.2 "1:10 定律"与设计先行

MASE 的设计哲学中有一条来自实践的铁律：**前期花 1 分钟澄清需求、明确边界，可以节省后期 10 倍的返工时间。**

这不是拍脑袋的数字。在实际项目中反复验证过：一个在 Proposal 阶段花 20 分钟用原型确认过的功能，Build 阶段的返工次数显著低于"边做边改"的功能。原因很简单——AI 看到原型就知道"用户要的是这个交互"，看到 Spec 就知道"验收标准是这些"，看到 Contract 就知道"边界不能逾越"。

设计先行不是"瀑布式"的复古——它是**在 AI 可以高速生成代码的时代，让方向确认跑在代码生成前面**。MASE 不是重流程，而是让流程的"重"集中在最值得重的地方：确认方向。

### 6.3 常驻 vs 按需：Token 经济学的设计

MASE 框架在上下文管理上的一个关键设计是**原则常驻 + 规范按需**的分层加载策略。

- 原则文件（`project-rules.md`）只有 70 行，9 条原则。它被 IDE 自动注入每一次对话的上下文。所以每一条原则都要精简到极限——只写"是什么"，不写"怎么做"。
- 规范文件（编码规范、设计原则、项目结构、术语表）独立存放，Agent 在特定场景下按需加载。编码时读 coding-standards.md，设计评审时读 design-principles.md，术语混淆时读 glossary.md。

这个设计的动机很实在：**原则文件每多一行，每次对话都多一份 token 成本。** 在 AI 编程场景下，上下文窗口是最稀缺的资源。把什么放进常驻上下文、什么按需加载，是一个需要持续优化的工程决策。

### 6.4 DoD 单一来源与门禁升级路径

MASE 的另一个关键设计原则是：**每个阶段的完成标准（DoD）只有一个权威来源——Agent 1 的门禁清单。** 其他文档只引用，不重复定义。

这个设计解决的是一个经典的文档腐烂问题：当 DoD 散落在 proposal.md、architecture.md、spec.md 等多个文件中时，迭代过程中必然出现不一致。A 文件改了但 B 文件没改，Agent 执行时不知道该信谁。

单一来源 + 引用模式确保了 DoD 的一致性。同时，每个门禁都有明确的升级路径——比如"同一 P0 E2E 场景连续 3 次修复仍失败 → 升级 Agent 1 决策（回退 Design 还是 Proposal）"。升级路径防止了 Agent 在门禁失败时陷入"反复修反复败"的死循环。

### 6.5 复盘即进化：PDCA 的真正闭环

MASE 最独特的一个阶段是 Retro（复盘）。大多数开发流程的"复盘"是形式化的——写个总结，下个结论，然后归档。MASE 的复盘是**框架自我进化的引擎**。

复盘的输入是：本轮所有 BUG 案例、所有经验教训记录、所有代码评审中的反复问题。复盘的输出是：复盘报告 + **改进措施**（更新 Skill 规则、补充代码规约、调整门禁 Checklist）。

这意味着：**MASE 框架本身是它的框架产出物之一。** 每一次项目复盘，都会反哺框架本身。一个项目发现"E2E 测试环境没有隔离导致测试不稳定"，复盘后 Sandbox 机制就被纳入了框架。一个项目发现"契约概念在框架中缺失导致边界 BUG 频发"，复盘后契约式开发就成为了第九条原则。

这就是 PDCA 的 Act 环节——不是"我们下次注意"，而是"我们把这次学到的东西编码进流程，下次自动执行"。

### 8.2 九大工程原则（完整版）

| # | 原则 | 一句话 |
|:-:|------|--------|
| R01 | 需求澄清确认 | 先确认真实需求，使用原型确认，不确认不推进 |
| R02 | 设计预研，消除风险 | POC 验证所有外部依赖，预研报告通过再架构设计 |
| R03 | 契约式约束 | 从 Spec 推导三层 DbC 契约，API 级硬性必做 |
| R04 | TDD 驱动 | 内外双循环 — 先写测试再写代码，E2E 测试同步编写 |
| R05 | 验证与确认检查 | E2E 自动化回归 + 人工探索性测试 + 合规审查 |
| R06 | 根因分析 | BUG 根因定位，避免盲目修改 |
| R07 | 系统化解决 | 不做临时补丁，A/B 双修 + 横向扫描同类风险 |
| R08 | 固定节奏提交 | 每 20 次对话或每个 Capability 完成时 git commit |
| R09 | 及时备份 | 删除代码或回退前做备份 |

### 8.3 未尽之路

MASE 仍在演化中。以下几个方向是现阶段明确但尚未完成的：

1. **跨项目模式提炼**：目前的实践经验集中在有限的项目上。当更多不同类型的项目接入 MASE 后，E2E 模式、契约粒度、Skills 组合等能否提炼为可配置的策略矩阵？

2. **Agent 1 自动化调度**：目前 Agent 1 的调度逻辑依赖人工判断（"现在应该启动 Agent 2 做 Proposal"）。能否基于 mase-state.yaml 实现自动阶段推进？

3. **度量驱动的流程优化**：MASE 框架本身的可度量性——每个阶段的耗时、返工率、BUG 引入阶段分布——这些数据如果系统化采集，能否驱动框架自身的优化？

4. **多语言/多框架适配**：目前的编码规范和项目结构主要面向 Python，扩展到 TypeScript/Go/Rust 等生态需要语言特定的规范补充。

## 结语

MASE 从一组碎片化的 AI 编程实践开始，经过 15 天的高强度迭代，演进为一套包含 Agent 架构、阶段流程、工程原则、质量防线、CLI 工具的完整方法论。

但 MASE 的价值不在于它"有什么"，而在于它回答了一个更根本的问题：**当我们有了一堆好用的 AI 编程工具之后，怎么让它们协作出一套真正靠谱的软件？**

答案只有六个字：**分工、门禁、闭环。**

分工让每个 Agent 做它最擅长的事。门禁让每个阶段的产出不可蒙混过关。闭环让每一次开发都在进化——上一次的教训变成下一次的规则。

而这六个字的背后，是 MASE 的核心信念：**AI 编程不是让流程更松散的理由，而是让流程更严谨的契机。**
